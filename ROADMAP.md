# uzbook — план разработки и релиза

> Обновлено: 27.10.2026  
> Текущий этап: стабилизация, production hardening, подготовка staging  
> Формат: этапы, результаты, критерии приёмки

## 1. Цель

Довести uzbook до стабильного коммерческого SaaS:

- владелец бизнеса без технических знаний запускает страницу записи и кабинет;
- клиент записывается без регистрации и сам управляет записью;
- платформа продаёт тарифы и контролирует лимиты;
- всё работает в браузере и Telegram;
- платежи проходят через Click, Payme, Telegram Stars и крипту;
- после web-версии выпускается мобильное приложение.

## 2. Принципы

1. **Сначала корректность, потом красота.** Не полируем UI поверх нестабильных сценариев.
2. **Один критический путь — сначала он.** Запись клиента, кабинет владельца, оплата тарифа.
3. **Безопасность и изоляция данных.** Каждый запрос ограничен своим `businessId`, роли проверяются на сервере.
4. **Маленькие релизы.** Один этап — один проверяемый результат, а не «большой запуск».
5. **Всё автоматизируем.** Типы, сборка, E2E, миграции, бэкапы, healthcheck.
6. **Мобильный клиент — после стабильного API.** Server Actions нельзя переиспользовать в приложении напрямую.

## 3. Текущее состояние

Уже работает:

- регистрация, онбординг, вход, роли `OWNER` / `SUPPORT` / `ADMIN`;
- публичная страница салона, услуги, мастера, расписание, запись без логина;
- управление записью по `/b/<token>`: перенос и отмена;
- кабинет владельца: таймлайн, услуги, мастера, записи, страница, галерея, QR;
- конструктор страницы: секции, тема, акцент, шрифты, порядок блоков через `dnd-kit`;
- тарифы, лимиты, trial, история подписок;
- платежи: Payme, Click, Telegram Stars, DEMO, MANUAL;
- админка: бизнесы, пользователи, заявки, MRR;
- Telegram-бот: привязка, `/today`, уведомления;
- Docker: PostgreSQL/PGlite, uploads, healthcheck, миграции.

Ключевые пробелы:

- Docker-образ ещё не запускался на реальном Linux-сервере;
- в рабочей БД есть демо-данные и демо-доступы;
- на `/login` показываются демо-пароли;
- в `PAYMENT_DETAILS` фейковая карта;
- истечение тарифа проверяется лениво, нет cron;
- нет возвратов, TTL платежа, rate limit webhook;
- криптооплата не реализована;
- нет публичного API для мобильного приложения;
- нет CI/CD, мониторинга и централизованных ошибок;
- нет полноценных E2E-тестов.

## 4. Рекомендуемая последовательность

| Этап | Название | Приоритет | Примерно |
|---|---|---|---|
| 0 | Аудит и стабилизация | P0 | 1–2 недели |
| 1 | Функциональная база кабинета owner | P0 | 2 недели |
| 2 | Визуал, UI/UX и motion | P1 | 2–3 недели |
| 3 | Telegram | P1 | 1–2 недели |
| 4 | Платежи beta | P1 | 2–3 недели |
| 5 | Мобильное приложение | P2 | 4–6 недель |

Почему owner-функции раньше визуала: сначала нужно зафиксировать сценарии и данные, которые будут на экранах. Иначе после каждого изменения логики придётся перерисовывать интерфейс.

Расширенные owner-функции (CRM, отчёты, пакеты услуг) можно делать после визуального этапа — они не блокируют запуск.

## 7. Этап 2 — Визуал, UI/UX и motion

**Результат:** продукт выглядит как платный сервис, а не как админка; запись приятно проходить с телефона.

### 7.1 Дизайн-система

- [ ] Токены: цвета, типографика, отступы, радиусы, тени, границы.
- [ ] Компоненты: кнопки, поля, карточки, модалки, таблицы, тосты, скелетоны.
- [ ] Светлая и тёмная темы без «вырвиглазных» контрастов.
- [ ] Единые состояния: hover, focus, active, disabled, loading, error.
- [ ] Иконки и иллюстрации в одном стиле.
- [ ] Правила адаптива: mobile-first, breakpoints, safe-area.

### 7.2 Публичная страница

- [ ] Hero с понятным оффером и CTA «Записаться».
- [ ] Блоки услуг, мастеров, галереи, отзывов, контактов.
- [ ] Sticky CTA на мобильном.
- [ ] Быстрый выбор услуги и мастера.
- [ ] QR и шаринг.
- [ ] Красивые пустые состояния, если владелец ещё не заполнил блоки.

### 7.3 Сценарий записи

- [ ] Пошаговый wizard: услуга → мастер → дата/время → контакты → подтверждение.
- [ ] Прогресс и возможность вернуться назад без потери данных.
- [ ] Календарь и слоты с понятной загрузкой.
- [ ] Валидация телефона и имени.
- [ ] Экран успеха с номером записи и ссылкой управления.
- [ ] Управление записью: перенос, отмена, понятные причины.
- [ ] Ошибки сети и повторная отправка без дублей.

### 7.4 Motion

- [ ] Переходы между шагами: fade/slide, без тяжёлого 3D.
- [ ] Появление слотов и карточек: stagger, но быстро.
- [ ] Микроанимации кнопок, выбора, чекбоксов.
- [ ] Анимация успешной записи: галочка/мягкий конфетти.
- [ ] Bottom sheet для выбора даты/мастера на мобильном.
- [ ] Skeleton-загрузка вместо резких скачков.
- [ ] `prefers-reduced-motion` — обязательно.
- [ ] Библиотека: `motion` (Framer Motion) для сложных переходов, CSS — для простых.
- [ ] Бюджет: не тащить анимации в критический бандл без необходимости.

### 7.5 Кабинет owner

- [ ] Таймлайн дня: drag, resize, конфликты, подсветка.
- [ ] Карточки загрузки, выручки, неявок.
- [ ] Графики и отчёты без визуального шума.
- [ ] Модалки и боковые панели вместо переходов на отдельные страницы там, где это ускоряет работу.
- [ ] Тосты и undo для опасных действий.
- [ ] Пустые состояния с подсказками.
- [ ] Мобильный кабинет: сегодня, записи, быстрые действия.

### 7.6 Доступность и производительность

- [ ] WCAG AA: контраст, фокус, клавиатура, aria.
- [ ] LCP < 2.5s на мобильном 4G.
- [ ] CLS < 0.1.
- [ ] INP < 200ms.
- [ ] Проверка в Chrome, Safari, Firefox, Android/iOS.
- [ ] Скриншот-тесты ключевых экранов.

### Критерии приёмки этапа 2

- запись с телефона проходит без зумов и горизонтального скролла;
- все ключевые экраны имеют loading/empty/error;
- анимации не мешают и отключаются при reduced motion;
- дизайн-система переиспользуется в публичной части и кабинете;
- нет тяжёлых layout shift на первом экране.

## 9. Этап 4 — Платежи beta

**Результат:** деньги принимаются автоматически, статусы сходятся, ошибки не теряются.

### 9.1 Матрица провайдеров

| Провайдер | Статус | Что проверить |
|---|---|---|
| Payme | sandbox → production | checkout, webhook, Cancel, GetStatement |
| Click | sandbox → production | Prepare, Complete, подпись, prepare_id |
| Telegram Stars | test → production | invoice, pre_checkout, successful_payment |
| Crypto | новый | провайдер или on-chain, подтверждения |
| Manual | уже есть | заявка, подтверждение админом |

### 9.2 Жизненный цикл платежа

- [ ] Статусы: created, pending, paid, canceled, expired, failed, refunded.
- [ ] TTL: неоплаченный платёж отменяется автоматически.
- [ ] Идемпотентность: повторный webhook не активирует тариф дважды.
- [ ] Сверка: платёж ↔ подписка ↔ период.
- [ ] Возврат и chargeback.
- [ ] Ручная отмена админом.
- [ ] Уведомление владельцу об успешной оплате.
- [ ] Админский журнал: кто, когда, что изменил.

### 9.3 Webhook-безопасность

- [ ] Проверка подписи Payme/Click.
- [ ] IP allowlist, если провайдер даёт стабильные адреса.
- [ ] Rate limit.
- [ ] Защита от replay.
- [ ] Логирование тела и результата без секретов.
- [ ] Алерт при массовых ошибках.

### 9.4 Крипта

Сначала выбрать модель:

- **Провайдер** (CryptoCloud, NOWPayments и аналоги) — быстрее, меньше своей ответственности;
- **On-chain** (USDT/TON) — больше контроля, но нужны подтверждения, курс, комиссии, мониторинг.

Минимум:

- [ ] Счёт в USDT/TON.
- [ ] Курс и сумма в UZS.
- [ ] Подтверждения сети.
- [ ] Идемпотентная активация.
- [ ] Возвраты/ручная обработка.
- [ ] Feature flag, чтобы включить после тестов.

### 9.5 Production cutover

- [ ] Реальные merchant-аккаунты.
- [ ] Публичный HTTPS и URL webhook.
- [ ] `PAYMENTS_DEMO=off`.
- [ ] Тестовая оплата на минимальную сумму.
- [ ] Сверка с провайдером.
- [ ] Инструкция для поддержки.

### Критерии приёмки

- полный цикл оплаты проходит на staging и production;
- повторный webhook не создаёт дубль;
- зависший платёж отменяется;
- возврат обработан;
- админ видит историю и может разобрать инцидент.

---

## 10. Этап 5 — Мобильное приложение

**Результат:** клиент записывается и управляет записью из приложения; владелец видит день и получает push.

### 10.1 Решение

Рекомендуется **Expo / React Native**:

- тот же TypeScript и React;
- можно переиспользовать типы, валидаторы и бизнес-логику;
- быстрее выпустить iOS/Android;
- проще найти разработчика.

Flutter — только если команда уже на нём.

### 10.2 Обязательное условие: API

Server Actions не подходят для мобильного клиента. Нужно:

- [ ] Публичный REST API `/api/v1` или tRPC.
- [ ] Токены доступа и refresh.
- [ ] Версионирование.
- [ ] Rate limit.
- [ ] OpenAPI/документация.
- [ ] Одинаковые правила валидации с web.

### 10.3 MVP приложения

Клиент:

- [ ] вход по телефону/коду или ссылке;
- [ ] список салонов / переход по QR;
- [ ] услуги, мастера, слоты;
- [ ] запись;
- [ ] мои записи, перенос, отмена;
- [ ] push-уведомления;
- [ ] deep links.

Владелец:

- [ ] сегодня;
- [ ] список записей;
- [ ] подтверждение/отмена;
- [ ] push о новой записи;
- [ ] быстрый переход в web-кабинет для сложных действий.

### 10.4 Инфраструктура

- [ ] Expo EAS Build.
- [ ] App Store / Google Play аккаунты.
- [ ] Push (Expo/FCM/APNs).
- [ ] Crash reporting.
- [ ] Аналитика.
- [ ] Политика конфиденциальности.
- [ ] Тест на реальных устройствах.

### Критерии приёмки

- клиент проходит запись без web;
- владелец получает push;
- deep link открывает нужную запись;
- приложение не дублирует записи при плохой сети;
- web и мобильное приложение используют один API.

## 11. Сквозные направления

### Безопасность

- [ ] Секреты только в env, не в git.
- [ ] Сильный `AUTH_SECRET`, ротация.
- [ ] Проверка ролей на сервере.
- [ ] Защита от IDOR: нельзя открыть чужой `businessId`.
- [ ] Валидация всех входных данных.
- [ ] Ограничение загрузок.
- [ ] Security headers.
- [ ] Аудит действий админа.

### Тестирование

- [ ] Unit: расчёт слотов, лимиты, платежи.
- [ ] Integration: API и БД.
- [ ] E2E: Playwright — запись, кабинет, оплата.
- [ ] Load: k6 — публичная страница и создание записи.
- [ ] Payment sandbox: отдельный чек-лист.

### Наблюдаемость

- [ ] Sentry.
- [ ] Структурированные логи.
- [ ] Uptime-мониторинг `/api/health`.
- [ ] Алерты: 5xx, webhook errors, очередь платежей.
- [ ] Дашборд: записи, оплаты, ошибки.

### CI/CD

- [ ] GitHub Actions: typecheck, build.
- [ ] Docker build/push.
- [ ] Миграции на staging.
- [ ] Ручной approve на production.
- [ ] Теги релизов.

### Документация

- [ ] README для разработчика.
- [ ] Runbook: деплой, откат, бэкап, восстановление.
- [ ] Инструкция для поддержки.
- [ ] Публичная документация API (после мобильного этапа).

## 12. Ориентировочный график

Оценка для одного разработчика с AI-ассистентом, без параллельной команды:

| Этап | Длительность | Результат |
|---|---:|---|
| 0. Аудит и staging | 1–2 недели | стабильная база, CI, HTTPS |
| 1. Owner-функции | 2 недели | кабинет закрывает день |
| 2. UI/UX + motion | 2–3 недели | продукт выглядит готовым |
| 3. Telegram | 1–2 недели | бот и Mini App |
| 4. Платежи beta | 2–3 недели | деньги и сверка |
| 5. Mobile MVP | 4–6 недель | iOS/Android |
| **Итого** | **12–18 недель** | коммерческий запуск |

Если нужен запуск раньше, можно выпустить web + Telegram + Payme/Click без крипты и мобильного, а мобильное сделать после первых платящих клиентов.

## 13. Release gates

Перед публичным запуском:

- [ ] нет P0-багов;
- [ ] критический E2E-путь зелёный;
- [ ] оплата проверена на реальном провайдере;
- [ ] `PAYMENTS_DEMO=off`;
- [ ] демо-данные и демо-доступы удалены;
- [ ] HTTPS и secure-cookie;
- [ ] бэкап и restore проверены;
- [ ] мониторинг и алерты включены;
- [ ] поддержка знает, как разобрать платёж;
- [ ] политика конфиденциальности опубликована.

## 14. Ближайшие 10 рабочих дней

1. **День 1–2.** Git, CI, проверка env, staging на VPS.
2. **День 3–4.** Убрать демо-доступы/фейковую карту/legacy-заявку из production-конфигурации.
3. **День 5–6.** E2E критического пути, фиксы P0.
4. **День 7–8.** Cron истечения подписок, TTL платежа, rate limit webhook.
5. **День 9–10.** Smoke на staging, backup/restore, список задач на owner-этап.

## 15. Git-процесс

- `main` — защищённая ветка, только через PR.
- `feat/...` — новая функциональность.
- `fix/...` — баги.
- `chore/...` — инфраструктура.
- Один PR — одна логическая задача.
- CI обязателен перед merge.
- Секреты — только в env/секретах репозитория.
- Релизы — тегами `v0.x.y`.

Репозиторий должен содержать:

- код;
- миграции;
- `.env.example`;
- Dockerfile и compose;
- README;
- этот roadmap;
- инструкции по деплою и бэкапу.

## 16. Риски

| Риск | Влияние | Снижение |
|---|---|---|
| Нет реальных merchant-ключей | нельзя проверить деньги | sandbox + staging + ранний запрос ключей |
| Payme/Click отклонят интеграцию | блокировка оплаты | тесты по документации, поддержка провайдера |
| Крипта: волатильность/комплаенс | потери/блокировки | провайдер, лимиты, ручная проверка |
| Telegram ограничит бота | потеря канала | web остаётся основным |
| PGlite на нескольких процессах | повреждение данных | production только PostgreSQL |
| Мобильное приложение потребует API | задержка | проектировать API до mobile |
| Расползание scope | срыв сроков | release gates и must/should/could |
| Один разработчик | bus factor | документация, CI, простые решения |

## 17. Что не делаем сейчас

- SMS и email-рассылки.
- Маркетплейс салонов.
- AI-рекомендации.
- Складской учёт.
- Мультивалютность.
- Сложную CRM-автоматизацию.

Эти функции — после стабильного запуска и первых платящих клиентов.
