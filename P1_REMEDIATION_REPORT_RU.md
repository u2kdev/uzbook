## 2. Детальный разбор исправлений

### 2.1. NEW-P1-1 — Утечка PII и секретных manageToken через GET /api/v1/bookings

#### Причина проблемы
Эндпоинт `GET /api/v1/bookings?phone=` позволял любому неавторизованному клиенту передать параметр `phone` и получить до 50 записей по всем салонам платформы, включая:
1. Персональные данные клиентов (ФИО, телефон, адреса посещённых салонов, стоимость услуг).
2. Секретный токен управления `manageToken` (`/b/[token]`).
3. Ссылку прямого управления `manageUrl`.

Злоумышленник мог перебирать номера телефонов и отменять либо переносить чужие записи через эндпоинты управления бронями.

#### Реализованное решение
1. **Строгая авторизация:** В `GET /api/v1/bookings` добавлена обязательная аутентификация через `authenticateBearer(request)`. Неавторизованные запросы немедленно отклоняются с кодом `401 Unauthorized`.
2. **Изоляция Multi-Tenant:** Выборка записей ограничена салоном владельца токена:  
   `where(and(eq(bookings.businessId, business.id), eq(bookings.clientPhone, normalized)))`. Владелец салона A видит историю клиента исключительно в рамках салона A и не имеет доступа к визитам в салон B.
3. **Исключение секретных токенов:** Поля `manageToken` и `manageUrl` полностью удалены из SQL-выборки `.select({...})` и финального JSON-ответа. Клиентский токен управления остаётся конфиденциальным для клиента, оформившего запись.
4. **Обновление документации и клиентов:**
   - В `src/app/api/v1/openapi.json/route.ts` эндпоинт переведён в тег `Owner Bookings` с требованием схемы `BearerAuth`.
   - В мобильном клиенте `mobile/src/api/client.ts` метод `getBookingsByPhone` переведён на `requiresAuth = true`, поля токенов помечены опциональными, а в `MyBookingsScreen.tsx` добавлены проверки безопасного доступа.

### 2.2. NEW-P1-2 — Обход блокировки истёкшей подписки и статуса SUSPENDED

#### Причина проблемы
Функция проверки прав на запись платного контента `writeBlockedReason(business)` проверяла только окончание триала (`business.plan === "TRIAL"`), но не учитывала статус `SUSPENDED` (приостановка салона администратором платформы) и статус `DRAFT`. Кроме того, вызовы `writeBlockedReason` отсутствовали в критических экшенах:
- Создание ручной записи владельцем (`createManualBookingAction`)
- Перенос записи владельцем (`ownerRescheduleBookingAction`)
- Смена статуса записи в админке салона (`setBookingStatus`) и REST API (`PATCH /api/v1/owner/bookings/[id]/status`)
- Добавление и редактирование клиентов в CRM (`saveClientAction`, `updateClientNotesAction`)
- Быстрые блокировки времени и расписания (`blockTimeAction`, `toggleDayOffAction`)
- Редактирование профиля салона (`updateProfileAction`)
- Создание онлайн-записей через `createBooking` (`src/server/booking/service.ts`)

В итоге салон с истёкшей подпиской или в статусе `SUSPENDED` продолжал принимать онлайн-записи и вести активную деятельность в CRM.

#### Реализованное решение
1. **Расширение `writeBlockedReason(business)`:**
   - Добавлена проверка `business.status === "SUSPENDED"` -> `"Бизнес приостановлен администратором. Обратитесь в поддержку."`.
   - Добавлена проверка `business.status === "DRAFT"` -> `"Бизнес не опубликован и находится в статусе черновика."`.
   - Сохранена проверка истёкшего триала `trialEndsAt < Date.now()`.
2. **Автоматическая актуализация статуса подписки:**
   - В `currentBusinessForOwner(ownerId)` интегрирован автоматический вызов `expireBusinessIfNeeded(business)`.
   - В `getBusinessBySlug(slug)` интегрирован вызов `expireBusinessIfNeeded(row)` — если оплаченный период подписки завершился, статус бизнеса автоматически переводится в `TRIAL` с прошедшей датой окончания.
   - В `authenticateBearer(request)` добавлена актуализация статуса через `expireBusinessIfNeeded`.
3. **Внедрение проверок в модули модификации:**
   - В `src/server/actions/bookings.ts`: функции `createManualBookingAction` и `ownerRescheduleBookingAction` блокируются при наличии `writeBlockedReason`.
   - В `src/server/actions/clients.ts`: функции `saveClientAction` и `updateClientNotesAction` блокируются при наличии `writeBlockedReason`.
   - В `src/server/actions/quick-actions.ts`: функции `blockTimeAction` и `toggleDayOffAction` блокируются при наличии `writeBlockedReason`.
   - В `src/server/actions/profile.ts`: функция `updateProfileAction` блокируется при наличии `writeBlockedReason`.
   - В `src/server/booking/service.ts`: `createBooking` блокирует создание новых записей в салон с истёкшей подпиской или статусом `SUSPENDED` (`error: "slot_unavailable"`).
4. **Безусловное сохранение безопасной отмены существующих записей:**
   - В `setBookingStatus`: если статус равен `"CANCELLED"`, проверка `writeBlockedReason` **не блокирует операцию**. Владелец может отменить ранее созданную запись даже при заблокированном тарифе.
   - В `PATCH /api/v1/owner/bookings/[id]/status`: аналогично, статус `"CANCELLED"` разрешён всегда; статусы `"CONFIRMED"`, `"COMPLETED"`, `"NO_SHOW"` блокируются кодом `403 plan_limit_reached`.
   - В клиентском `cancelBooking(token)`: отмена клиентом остаётся доступной.

### 2.3. NEW-P1-3 — Обход лимита MAX_ACTIVE_BOOKINGS_PER_PHONE через сессию

#### Причина проблемы
В публичном эндпоинте создания брони `POST /api/public/[slug]/bookings` (`src/app/api/public/[slug]/bookings/route.ts:63-64`) присутствовал код:
```ts
const session = await getSession();
const source: "WEB" | "MANUAL" = session ? "MANUAL" : "WEB";
```
Если запрос отправлял любой авторизованный в системе пользователь (например, владелец другого салона или клиент с сессионной cookie), `session` была не пустой. В результате запись помечалась источником `"MANUAL"`, что полностью отключало анти-спам лимит `MAX_ACTIVE_BOOKINGS_PER_PHONE` (максимум 5 активных предстоящих записей на один номер телефона в салоне).

#### Реализованное решение
Условие назначения источника `"MANUAL"` изменено на строгую проверку авторизации относительно конкретного целевого салона:
```ts
const session = await getSession();
const isAuthorizedOwner = Boolean(
  session && (session.id === business.ownerId || session.role === "ADMIN"),
);
const source: "WEB" | "MANUAL" = isAuthorizedOwner ? "MANUAL" : "WEB";
```
1. Если запрос исходит от действительного владельца этого салона (`session.id === business.ownerId`) или администратора платформы (`session.role === "ADMIN"`), запись создаётся как `"MANUAL"` (ручная запись клиенту без спам-ограничений).
2. Любые другие пользователи (включая владельцев других салонов, провайдеров, обычных пользователей и анонимных гостей) получают источник `"WEB"`, для которого строго действует лимит 5 активных записей.

## 4. Итоговая оценка безопасности

После устранения трёх замечаний категории P1:
1. Полностью исключена возможность перехвата броней и утечки персональных данных клиентов через эндпоинты поиска по телефону.
2. Закрыты все пути обхода тарифных ограничений для салонов с истёкшей подпиской и салонов, заблокированных администрацией платформы (`SUSPENDED`).
3. Защищён от обхода механизм защиты от спам-бронирований.
4. Сохранены все критически важные функции непрерывности обслуживания клиентов (безопасная отмена записей клиентами и владельцами).

Все требования этапа выполнены в полном объёме.
